# Pediatric Infusion Simulator — спецификация первой версии

Дата: 2026-10-08
Статус: согласовано в обсуждении, ждёт проверки файла

## 1. Цель

Интерактивный мобильный симулятор инфузионной терапии для обучения студентов
безопасному программированию инфузионных насосов и контролю правильности
дозирования. Инфузомат — только интерфейс; суть проекта — симуляция
клинического принятия решений и предотвращение ошибок.

Первая версия делается для студенческой ярмарки: посетитель сканирует QR-код,
проходит сценарий на своём телефоне за 3–4 минуты, его результат появляется
в рейтинге на экране стенда.

## 2. Границы первой версии

Входит:

- мобильный веб-сайт (телефон в вертикальном положении, планшет, ноутбук);
- виртуальный инфузомат (собственная цифровая модель, обобщённая, без логотипов
  производителей);
- 5 клинических сценариев, расчёт дозировки, программирование насоса, тревоги;
- два режима: «Начать симуляцию» (с подсказками) и «Тестовый режим» (без подсказок);
- раздел «Обучение» из 4 карточек;
- баллы, ошибки, критические ошибки, итог «сдано / не сдано»;
- бэкенд: сохранение результатов с пересчётом баллов на сервере, рейтинг,
  модерация;
- экран стенда с QR-кодом и рейтингом;
- интерфейс на русском и казахском с переключателем.

Не входит: физический насос на ESP32, кабинет преподавателя, вход по паролю,
редактор сценариев, офлайн-режим (PWA), сценарии сверх пяти.

## 3. Экраны и маршруты

| Маршрут | Экран |

| `/scenarios?mode=learning\|exam` | Выбор сценария: 5 карточек (пациент и тема). Пока сценарий не проверен преподавателем, на карточке значок «Черновик». |
| `/sim/[scenarioId]?mode=learning\|exam` | Симуляция (см. раздел 5). Перед первой симуляцией — ввод ника. |
| `/learn` | Обучение: 4 карточки — кнопки инфузомата; формула дозы; формула скорости и времени; тревоги и действия. |
| `/results` | «Мои прохождения» (с этого телефона) и общий рейтинг с вкладками «Тестовый режим» / «С подсказками», период «Сегодня» / «Всё время». |
| `/stand` | Экран стенда: большой QR-код на адрес сайта, кнопка «Скачать QR (PNG)», два рейтинга рядом, обновление каждые 10 секунд, период «Сегодня». |

Под полем — «Ник будет виден в общем рейтинге».

## 4. Режимы

| | С подсказками (`learning`) | Тестовый (`exam`) |
|---|---|---|
| Проверка ответа | сразу, ✅ / ❌ с пояснением | только в итоге |
| Попытки на шаг | несколько; баллы ×1 / ×0,5 / ×0 за 1-ю / 2-ю / 3-ю и далее; после 3-й неверной показывается правильный ответ | одна |
| Формулы | показываются на шагах расчёта | не показываются |
| START с неверными RATE/VTBI | программа останавливает запуск: «ОШИБКА НАСТРОЙКИ. Установленная скорость не соответствует назначению»; после 3-й неверной попытки показываются назначенные значения | насос запускается, ошибка фиксируется |
| START без двойной проверки | запуск блокируется: «Сначала выполните двойную проверку» | насос запускается, ошибка фиксируется |
| Тревога | после неверного действия подсказка следующего шага | без подсказок; после 3 неверных действий тревогу «устраняет старший коллега», за тревогу 0 баллов |

## 5. Ход одной симуляции

1. Карточка пациента: номер, возраст, масса, состояние, установленные доступы, назначение.
2. Выбор препарата из 3 вариантов (правильный и похожие).
3. Выбор пути введения: ПВК, ЦВК, PICC, внутрикостный доступ.
4. Расчёт: 1–2 числовых шага; число вводится вместе с единицей из списка
   (`UnitId`: `mg`, `g`, `ml`, `ml_h`, `mg_kg`, `ml_kg`, `mg_ml`).
5. Программирование инфузомата и двойная проверка: чек-лист из 5 пунктов
   (пациент; препарат и концентрация; доза и объём; путь введения; скорость и
   время). Когда отмечены все пункты, записывается событие `checklistCompleted`.
6. START → ход инфузии в ускоренном времени; в сценариях 2–4 — тревога.
7. Итог: баллы из 100, разбивка по категориям, список ошибок, время, «сдано / не сдано».
   Результат сохраняется на телефоне и отправляется на сервер.

## 6. Логика (модули `lib/engine`, чистый TypeScript)

### 6.1 `calc` — формулы

- доза (мг) = доза на кг (мг/кг) × масса (кг);
- объём (мл) = доза (мг) ÷ концентрация (мг/мл);
- объём по массе (мл) = мл/кг × масса;
- скорость (мл/ч) = объём (мл) ÷ время (ч);
- поддерживающая скорость по 4-2-1 (мл/ч) = 4 × первые 10 кг + 2 × следующие 10 кг + 1 × каждый кг сверх 20;
- скорость по GIR (мл/ч) = GIR (мг/кг/мин) × масса × 60 ÷ концентрация (мг/мл);
- время (ч) = VTBI ÷ скорость.

Скорость и VTBI округляются до 0,1. Ожидаемые значения сценария не пишутся
вручную: они вычисляются этими функциями из назначения (раздел 7).

### 6.2 `pump` — инфузомат

Кнопки: `POWER`, `MENU`, `LEFT` (◀), `RIGHT` (▶), `PLUS` (+), `MINUS` (−),
`ENTER`, `START`, `STOP`, `MUTE` (без звука).

Пределы: RATE 0,0–999,9 мл/ч; VTBI 0,0–9999,9 мл.

Состояния:

- `off` — `POWER` включает насос (на экране «SELF TEST… OK», анимация 1,5 с,
  на логику не влияет) → `program`.
- `program` — на дисплее препарат из библиотеки (тот, что студент выбрал на шаге 2),
  RATE, VTBI и вычисленный TIME. `MENU` переключает поле RATE ↔ VTBI.
  `ENTER` начинает редактирование выбранного поля: курсор стоит на старшем
  разряде, `LEFT` / `RIGHT` двигают курсор, `PLUS` / `MINUS` меняют цифру
  (0–9 по кругу), `ENTER` сохраняет, `STOP` отменяет.
  Если сохраняемая скорость выше `softMax` или ниже `softMin` библиотеки
  выбранного препарата — состояние `limitWarning`: «⚠ RATE ABOVE LIMIT / BELOW
  LIMIT. Проверьте скорость»; `ENTER` подтверждает (фиксируется как
  «предупреждение проигнорировано»), `STOP` возвращает к редактированию.
  `START` при RATE = 0 или VTBI = 0 — короткий сигнал, состояние не меняется.
  `START` в остальных случаях → `confirm`.
- `confirm` — сводка RATE / VTBI / TIME. `START` — попытка запуска (раздел 6.4),
  `STOP` — назад в `program`.
- `running` — модельное время идёт, растёт введённый объём (VI), убывает TIME LEFT.
  `STOP` → `paused`. Остальные кнопки, кроме `MUTE`, не действуют.
- `paused` — «PAUSED»; `START` → `running`, остальные кнопки, кроме `MUTE`, не
  действуют. Перепрограммировать насос после запуска нельзя.
- `alarmStopped` — инфузия остановлена тревогой (OCCLUSION, AIR IN LINE,
  BATTERY EMPTY); выход — по правилам раздела 6.5.
- `complete` — «VTBI INFUSED», сигнал; `MUTE` гасит сигнал; симуляция переходит к итогу.

Тревога — отдельное поле насоса (`alarm: null | { type, fixed }`). При OCCLUSION и
AIR IN LINE насос переходит в `alarmStopped`; при LOW BATTERY остаётся в `running`.
`MUTE` в любой момент гасит звук и на баллы не влияет.

Ускорение времени: коэффициент = max(1, модельная длительность (с) ÷ 60),
то есть инфузия длится около минуты. Переключатель «Реальное время» ставит ×1.
На баллы ускорение не влияет.

### 6.3 Журнал действий

Сессия — это список событий; состояние сессии получается сворачиванием событий
функцией `applyEvent(session, event)`. Клиент и сервер используют одну и ту же
функцию, поэтому сервер может пересчитать результат.

```ts
type SimEvent =
  | { type: 'drugSelected'; optionId: string; t: number }
  | { type: 'routeSelected'; routeId: 'piv' | 'cvc' | 'picc' | 'io'; t: number }
  | { type: 'calcAnswered'; stepId: string; value: number; unit: UnitId; t: number }
  | { type: 'pumpButton'; button: PumpButton; t: number }
  | { type: 'checklistCompleted'; t: number }
  | { type: 'alarmRaised'; alarm: 'occlusion' | 'airInLine' | 'lowBattery'; t: number }
  | { type: 'batteryDepleted'; t: number }
  | { type: 'alarmAction'; actionId: string; t: number }
  | { type: 'infusionCompleted'; t: number };
```

`t` — миллисекунды от начала сессии, не убывают. События, которые генерирует
модельное время (`alarmRaised`, `batteryDepleted`, `infusionCompleted`),
записывает клиент; `applyEvent` принимает их только в допустимом состоянии
(тревога — только та, что задана сценарием, только во время инфузии и один раз;
завершение — только во время инфузии без активной тревоги). Недопустимое
событие — ошибка разбора журнала.

### 6.4 `grading` — баллы

| Категория | Баллы | Правило |
|---|---|---|
| Препарат | 15 | выбран правильный вариант |
| Путь введения | 15 | выбран допустимый для сценария и установленный у пациента доступ |
| Расчёт | 20 | делится поровну между шагами расчёта; верно = значение в пределах 0,05 и верная единица (верное значение с неверной единицей — `wrongUnit`, иначе `wrongCalc`) |
| Скорость | 20 | RATE в момент запуска равен ожидаемому (в пределах 0,05) |
| Объём (VTBI) и время | 10 | VTBI в момент запуска равен ожидаемому (в пределах 0,05); TIME тогда тоже верен |
| Двойная проверка | 10 | чек-лист пройден до запуска |
| Тревога / без ошибок | 10 | есть тревога — по правилам раздела 6.5; нет тревоги — 10, если за сессию не было ни одной ошибки |

- Попытка для категорий «Скорость», «VTBI» и «Двойная проверка» — каждое
  нажатие `START` в состоянии `confirm`; одно нажатие — попытка сразу для всех
  трёх. Баллы каждой из трёх категорий определяются номером первой попытки, на
  которой именно эта категория была верной (×1 / ×0,5 / ×0). В режиме с
  подсказками попытка, где неверна хотя бы одна из трёх, отклоняется, и насос
  возвращается в `program`; в тестовом первая попытка окончательная и запускает
  инфузию.
- Итог = округлённая сумма баллов, 0–100.
- Критические ошибки фиксируются в обоих режимах, даже если в режиме с
  подсказками ошибку потом исправили (итог «не сдано» при любых баллах):
  - выбран препарат, помеченный в сценарии как критический (NaCl 10%, глюкоза 40%);
  - выбран путь, помеченный как критический (сценарий 5: ПВК);
  - запуск со скоростью, отличающейся от назначенной в 2 раза и более в любую
    сторону (константа `CRITICAL_RATE_RATIO = 2`).
- Коды ошибок (показываются в итоге): `wrongDrug`, `criticalDrug`,
  `routeNotAvailable`, `wrongRoute`, `criticalRoute`, `wrongCalc`, `wrongUnit`,
  `wrongRate`, `criticalRate`, `wrongVtbi`, `ignoredLimitWarning`,
  `startWithoutCheck`, `wrongAlarmAction`, `restartWithoutFix`,
  `stoppedNeedlessly`, `batteryDepleted`.

### 6.5 Тревоги

Общее: при тревоге звучит сигнал (Web Audio), телефон вибрирует там, где это
поддерживается, индикатор красный (для LOW BATTERY — жёлтый). Под насосом
появляется панель «Действия» — правильные и неверные варианты в перемешанном
порядке. `MUTE` гасит звук; `STOP` при OCCLUSION и AIR IN LINE допустим (насос и
так остановлен) — оба на баллы не влияют.

| Тревога | Сценарий | Момент | Поведение насоса | Правильный порядок | Неверные варианты |
|---|---|---|---|---|---|
| OCCLUSION | 2 | 40 % | `alarmStopped` | «Осмотреть линию от насоса до пациента» (показывает причину: закрыт роликовый зажим ниже насоса) → «Открыть роликовый зажим» → `START` | «Промыть катетер с усилием», «Увеличить скорость, чтобы продавить линию», «Выключить и включить насос» |
| AIR IN LINE | 3 | 50 % | `alarmStopped` | «Перекрыть зажим линии к пациенту» → «Удалить воздух из линии по инструкции насоса» → «Открыть зажим» → `START` | «Отключить датчик воздуха», «Промыть катетер, чтобы протолкнуть пузырь» |
| LOW BATTERY (10 %) | 4 | 30 % | продолжает работать | «Подключить насос к сети» | «Выключить насос, чтобы сберечь заряд», «Вынуть аккумулятор»; `STOP` = `stoppedNeedlessly` (насос встаёт на паузу, `START` продолжает) |

- Тревога OCCLUSION / AIR IN LINE устранена, когда после всех действий нажат
  `START`; LOW BATTERY — когда выбрано «Подключить насос к сети».
- `START` при OCCLUSION / AIR IN LINE до устранения причины — `restartWithoutFix`
  (считается неверным действием), насос остаётся в `alarmStopped`.
- LOW BATTERY: если к 70 % насос не подключён к сети — событие `batteryDepleted`,
  насос переходит в `alarmStopped` («BATTERY EMPTY»); нужно подключить к сети и
  нажать `START`; за тревогу 0 баллов.
- Баллы за тревогу: 10 — все шаги в правильном порядке и без неверных действий;
  5 — тревога устранена, но порядок нарушен или было 1–2 неверных действия;
  0 — 3 и более неверных действия или `batteryDepleted`.

Пределы неверных препаратов — правдоподобные учебные значения, задаются в

Источники (для проверки преподавателем):

- инструкции по применению парацетамола для в/в введения и цефтриаксона; BNF for Children;
- WHO. Pocket Book of Hospital Care for Children, 2nd ed., 2013 — план C;
- Holliday M.A., Segar W.E. Pediatrics, 1957; NICE NG29 (IV fluid therapy in children);
- ASPEN — предел осмолярности для периферического введения, глюкоза > 12,5 % только центрально.

## 8. Бэкенд

Next.js Route Handlers в том же проекте; база — Postgres (Neon) через Vercel
Marketplace; драйвер `@neondatabase/serverless`; проверка входных данных — `zod`.

### 8.1 API

`POST /api/results`

```json
{
  "id": "uuid прохождения (создаёт клиент)",
  "nickname": "строка 2–20 символов",
  "scenarioId": "s1-paracetamol",
  "mode": "learning | exam",
  "locale": "ru | kk",
  "appVersion": "1.0.0",
  "events": [ /* SimEvent, не больше 1000 */ ]
}
```

- Сервер проверяет формат, ник (длина, буквы любого алфавита, цифры, пробел, `_`, `-`,
  фильтр нецензурных слов), сворачивает журнал через `applyEvent`, считает баллы
  через `grading`. Длительность = `t` последнего события, не больше 2 часов.
- Ответ `201` с `{ id, score, passed, breakdown, errors }`; повтор с тем же `id` —
  `200` с сохранённым результатом (идемпотентность для повторной отправки).
- `400` — неверный формат или ник; `422` — журнал не разбирается или симуляция
  не завершена.

`GET /api/leaderboard?mode=learning|exam&since=<ISO-время>&scenario=<id>`

- Лучшее прохождение каждого ника (без учёта регистра), скрытые записи не учитываются.
- Сортировка: сначала «сдано», затем баллы по убыванию, затем длительность по возрастанию.
- Топ-20: `{ nickname, score, passed, durationSec, scenarioId, createdAt }`.
- `since` считает клиент (например, начало сегодняшнего дня по его часам);
  без `since` — за всё время.

`GET /api/admin/results?limit=50` и `POST /api/admin/hide { id }`

- Заголовок `Authorization: Bearer <ADMIN_TOKEN>`, сравнение без утечки по времени;
  неверный ключ — `401`.

### 8.2 Таблица `results` (`db/schema.sql`)

```sql
create table if not exists results (
  id uuid primary key,
  nickname text not null check (char_length(nickname) between 2 and 20),
  scenario_id text not null,
  mode text not null check (mode in ('learning', 'exam')),
  score integer not null check (score between 0 and 100),
  passed boolean not null,
  breakdown jsonb not null,
  errors jsonb not null,
  events jsonb not null,
  duration_sec integer not null check (duration_sec >= 0),
  locale text not null check (locale in ('ru', 'kk')),
  app_version text not null,
  hidden boolean not null default false,
  created_at timestamptz not null default now()
);
create index if not exists results_board_idx
  on results (mode, created_at desc) where not hidden;
```

IP-адреса и другие данные о человеке не хранятся.

### 8.3 Хранилище

Интерфейс `ResultsRepo` с двумя реализациями: `PostgresRepo` (по `DATABASE_URL`)
и `MemoryRepo` (для разработки и сквозного теста). `MemoryRepo` используется
только если `DATABASE_URL` не задан и при этом `NODE_ENV !== 'production'` или
`ALLOW_MEMORY_STORE=1`; иначе сервер отвечает ошибкой, а не теряет данные молча.

## 9. Данные на телефоне

## 11. Внешний вид

- Насос — SVG и CSS: светлый корпус, подсвеченный дисплей, объёмные кнопки,
  индикаторы зелёный / жёлтый / красный, значок батареи и сети.
- Над насосом анимация «пакет → капельная камера → линия → насос → пациент»:
  уровень в пакете убывает, капли падают в такт скорости.
- Рассчитано сначала на телефон; на ширине от 768 px насос и карточка пациента
  стоят рядом. Кнопки не меньше 44 px.
- Стили — Tailwind CSS; цвета через CSS-переменные.

## 13. Тестирование

- Vitest, тесты пишутся до кода, для `calc`, `pump`, `session`, `grading`:
  - формулы и округление;
  - переходы насоса: ввод цифр, `MENU`, мягкие пределы, `confirm`, пауза;
  - тревоги: правильный порядок, неверные действия, `restartWithoutFix`, `batteryDepleted`;
  - баллы в обоих режимах, правило попыток, критические ошибки;
  - отказ разбора недопустимого журнала.
- Тест согласованности сценариев: ожидаемые значения из `calc` совпадают с
  таблицей раздела 7; правильный препарат и путь есть среди вариантов;
  правильная скорость лежит внутри пределов библиотеки; правильный путь
  установлен у пациента.
- Тесты API на `MemoryRepo`: проверка входных данных, пересчёт баллов (клиентские
  баллы игнорируются), идемпотентность, сортировка рейтинга, скрытие, `401`.
- Playwright, экран телефона: пройти сценарий 1 в режиме с подсказками → увидеть
  итог → увидеть ник в рейтинге (`next build && next start` с `ALLOW_MEMORY_STORE=1`).

   страницы `/stand`.

## 15. Риски и открытые вопросы

- Клинические данные — черновик; до ярмарки их проверяет преподаватель и
  переводит `reviewStatus` в `reviewed`.
- Казахские тексты — машинный уровень качества до вычитки.
- Vercel MCP пока без доступа к команде пользователя; на деплой не влияет (CLI).
- На ярмарке может быть плохая связь: симуляция работает без сети, результаты
  ждут в очереди.
